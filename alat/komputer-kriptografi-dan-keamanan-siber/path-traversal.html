Playground Path Traversal

Server tiruan di bawah "melayani" file dari satu folder yang diizinkan. Coba minta nama file yang aneh-aneh, dan lihat tiga cara server bisa menanganinya — satu yang aman, satu yang terlihat aman tapi sebenarnya tidak.

🎓 Ini pembelajaran defensif: memahami kenapa validasi input harus benar, supaya Anda bisa menulis kode server yang tidak kebobolan — bukan tutorial menyerang server sungguhan. Filesystem di bawah 100% tiruan (objek JavaScript di memori), tidak menyentuh sistem file sungguhan sama sekali.
📁 /var/www/uploads/ ← folder yang DIMAKSUDKAN bisa diakses publik
  ├─ laporan-bulanan.pdf
  ├─ foto-profil.jpg

📁 /var/www/ ← di luar folder publik
  └─ config.php (berisi kredensial database)
📁 /etc/
  └─ passwd (daftar akun sistem)

Kenapa "menghapus ../" saja tidak cukup

Coba pilih mode "Validasi naif", lalu tekan preset ketiga (....//....//....//etc/passwd). Filternya cuma mencari dan menghapus kemunculan teks "../" — tapi begitu bagian tengahnya terpotong, sisa karakter di kiri-kanan yang tadinya terpisah kini nempel jadi "../" yang baru, dan filter itu tidak pernah mengecek ulang hasilnya. String yang tadinya terlihat aman berubah jadi ../../../etc/passwd tepat setelah "dibersihkan".

Ini pola umum di balik banyak celah path traversal sungguhan: developer mencoba membersihkan input yang jahat (blacklist), padahal cara yang benar adalah menyelesaikan (resolve) path itu ke bentuk absolutnya dulu, baru mengecek apakah hasilnya masih berada di dalam folder yang diizinkan — apa pun bentuk input mentahnya. Validasi yang bekerja di level hasil akhir jauh lebih sulit dilubangi dibanding validasi yang bekerja di level pola teks mentah.

Bagian dari Laboratorium JAZMI — filesystem, path resolver, dan respons di atas seluruhnya simulasi di dalam browser Anda.
